## Follow-up: why the identity mutation killed only 9 of 109

The original mutation replaced `matched = [ref for detail, ref in details if detail is MatchDetail.NAME_AND_DOB_MATCH]` with `matched = [ref for detail, ref in details]` in `IdentityVerifier.verify()` (`src/callbot/engine/verification/identity.py:224`). It bypasses the match decision when at least one reference and both parsed claims exist. It does not bypass the guards for missing name/DOB, unavailable or empty references, or the inbound rule that two matched candidates are ambiguous. `match_record()` itself still computes correct details, but `verify()` discards them. Thus 9/109 is the kill rate for this mutation in **three selected scenario modules**, not for every identity-related test in the repository.

| Selected suite | Collected | RED | Green, with main reason |
|---|---:|---:|---|
| `test_identity.py` | 21 | 6 (`TC_ID_02/03/04/16/17/18`) | 15: correct identity, partial/invalid input, failed understanding, or zero lookup candidates. `TC_ID_19` has zero candidates because its phone is unseeded. |
| `test_identity_dialogue.py` | 78 | 1 (`test_wrong_identity_transfers_at_once_without_saying_which_field`) | 77: primarily prompt/recovery/lookup cases or correct identity; many nodes are wording parameters of the same branch. |
| `test_sf03_appointment_disclosure.py` | 10 | 2 (`TC_SF03_07/08`) | 8: `TC_SF03_01..06` stop before a complete wrong name+DOB pair; `TC_SF03_09` tests open prompts; `TC_SF03_10` tests synthetic leakage canaries. |
| **Total** | **109** | **9** | **100** |

Baseline was 109/109 PASS. Under the mutation, the six `TC_ID` cases fail at `test_identity.py:194` (`AWAITING_INTENT` instead of `ENDED`); the dialogue mismatch test fails its `_ended()` outcome check, and the two SF-03 cases fail at `_run_case()` in `test_sf03_appointment_disclosure.py:131` on the same state mismatch. These failures occur **before** `assert_no_appointment_disclosure()` runs. `TC_SF03_07` also contains an alternate wrong-DOB variant, but the first failing variant stops that test node before the alternate executes. This distinguishes an observed red test from a direct assertion of the leaked utterance.

A direct offline probe with a one-patient FakeClinicAPI and the wrong name / correct DOB shows the consequence:

| Direction | Baseline | Mutant |
|---|---|---|
| Outbound | `ENDED`, `TRANSFERRED`, `IDENTITY_FAILED` | `AWAITING_INTENT`, `identity_step=VERIFIED`, `patient_id=pt_3391`; the utterance reads department, 9 a.m., 14 October, and Vinmec Times City. |
| Inbound | `ENDED`, `TRANSFERRED`, `PATIENT_NOT_FOUND` | `AWAITING_INTENT`, `identity_step=VERIFIED`, `patient_id=pt_3391`; no appointment facts are spoken at that turn because the inbound call has no appointment yet. |

The attack path is therefore severe, but the interpretation "100 tests claiming to stop wrong identity stayed green" is unsupported. The six mismatch cases in the identity matrix all turned red. The denominator included positive cases and cases that never reached the matcher. Also, the original 109 excluded two relevant verifier/flow suites: their baseline was 38/38 PASS and the same mutation made **12/38 RED** (wrong name/DOB, unverifiable reference, and multi-candidate selection). Across those five suites the observed count is **21/147 RED**. A stronger mutation making `match_record()` always return `NAME_AND_DOB_MATCH` produced **23/156 RED** when a direct matcher test and eight name-normalization parameters were added. Both mutants were restored byte-for-byte.

Remaining test risks and concrete follow-ups:

1. Add an always-running HTTP test with a wrong but valid name+DOB pair, asserting the full utterance, `TRANSFERRED` reason, zero confirm writes, and the authoritative Clinic record. The four real cross-service tests are skipped by default and could not reach business assertions in this audit because Redis was unavailable.
2. Run the SF-03 disclosure checker before the expected-state assertions so a fail-open transcript is inspected even when the state is already wrong. In `test_identity.py`, do not truncate identity-failure actions at the first `AWAITING_INTENT` reported by the bot. Keep the state assertions too.
3. Repair `TC_ID_19` by seeding two patients on the queried phone and asserting the candidate count before testing ambiguity. Add a separate inbound one-candidate wrong-identity HTTP case.
4. For each identity-failure case, assert the authoritative Clinic status and unchanged protected fields, alongside the existing outcome and write-log assertions.

## Ambiguity phát hiện thêm khi audit

- Rev 1.0 §1.1.7 requires UNREACHABLE after three consecutive silences, without explicitly excluding inbound calls. Rev 1.0 §1.1.8 only redirects inbound identity rules from §1.1.1 to §1.1.9/§1.1.10. Inbound TRANSFERRED on silence is implementation policy; do not attribute it directly to Rev 1.0.
- Rev 1.0 has no §4.2.5 and its §4.2 endpoint table omits `/unreachable`, although §1.1.7 and §2.2 require an UNREACHABLE end state. Several test docstrings cite later Rev 1.1 text as Rev 1.0.
- Appendix A of Rev 1.0 lists `transfer_reason` and `cancel_reason`, but no `unreachable_reason` enumeration. The four unreachable reasons in local tests are an implementation enum.
- §6.1 leaves wording, hesitation recovery and repeat requests to the team. Such tests may honestly encode implementation policy, but cannot prove a MUST that Rev 1.0 never states.
